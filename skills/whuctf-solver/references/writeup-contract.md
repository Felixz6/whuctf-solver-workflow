# WP 质量约定

`python3 prep/scripts/whuctf.py check <题目目录>` 只做结构检查。它不判断推理是否正确，也不访问题目服务或平台。下面第一节是它的通过条件；第二节是写作要求，检查器不会逐条执法。

## 结构检查

退出码 0 表示下面各项都满足。退出码 1 时，标准输出里每条 `FAIL:` 对应一个问题。退出码 2 表示题目目录本身打不开，不是 WP 内容问题。

### flag.txt

- 必须是 UTF-8 文本文件。
- 读入时 CRLF 和 LF 都视为换行，然后只去掉至多一个结尾换行。
- 剩下的整段必须匹配 `prep/whuctf-profile.json` 里的某个 `flag_prefixes`，形式是 `前缀{正文}`。正文不能为空，也不能再含花括号。
- 除已经被去掉的结尾换行外，不能含控制字符。`valid_flag` 本身不修剪空白；文件读取才会去掉那一个换行。

### WP 章节

- 二级标题写成 `## 数字. 标题`，数字从 1 连续增加到末节。无编号的 `##` 标题不算通过。
- 三个标题必须出现：`初步观察与分析路线`、`逐步分析与解题`、`完整 flag`。第一节必须是前者，最后一节必须是后者。中间可以按实际过程增加章节，例如「完整利用脚本」。
- `###` 小节不算新的章节，编号也不必满足上面的连续整数规则。
- 成对的代码块会先被去掉，再统计标题。代码块里的 `## ` 不会变成章节，也不会把上一节截断。
- 不能使用已取消的标题：`题目与目标`、`环境与原始证据`、`失败尝试与路线调整`、`最终复现`、`Flag 与验证`、`参考资料`，以及任何以 `附录` 开头的标题。
- 以行首 ` ``` ` 计数，奇数表示代码块未闭合。
- 去掉代码块后的正文或标题里出现 `{{...}}`、独立的 `TODO` 或 `TBD` 会失败。成对代码块内的同名字面量不计入，以免误伤完整脚本。
- `初步观察与分析路线` 和 `逐步分析与解题` 两节里，去掉空白和代码块后至少各有 45 个字符。只贴脚本通不过。
- `完整 flag` 一节的正文只能是 flag 本身，或下面两种代码块之一。允许四周空白，其后不能再有别的段落：

```text
前缀{正文}
```

或信息字符串为空的代码块。没有正文、标题后直接结束文件，也算失败。flag 字符串还必须在 WP 的某处出现；只写在 `flag.txt` 里不够。

### 验证记录

必须有 `evidence/validation.json`，且是一个对象：

```json
{
  "kind": "reconstructed_checker",
  "accepted": true,
  "exit_status": 0,
  "command": ["实际命令", "参数"],
  "input": "实际输入",
  "output_file": "evidence/output.txt",
  "output_sha256": "该文件的 sha256"
}
```

- `kind` 只能是 `original_checker`、`reconstructed_checker`、`remote_response`、`platform_accepted` 之一，对应原校验器、重建校验、题目服务响应和平台接受。检查器只核对取值，不能证明这个层级是真的。
- `accepted` 必须是 JSON 布尔值 `true`。数字 `1` 不算通过。`exit_status` 必须是 `0`。
- `command` 必须非空，可以是字符串或数组。`input` 键必须存在，值可以是空字符串。
- `output_file` 指向题目目录内的普通文件。相对路径不能含 `..`，也不能是符号链接或管道。落在题目目录内的绝对路径可以使用。SHA-256 必须与文件字节一致，且这些字节里要能找到 `flag.txt` 中的 flag（UTF-8）。

### manifest

没有 `manifest.json` 时不查原件。有的话，`files` 里每一项的 `archived` 必须是 `original/` 下的普通文件，不能是绝对路径、`..` 或符号链接，且 SHA-256 与记录一致。`original` 目录本身也不能是符号链接。

## 写法

这些要求靠作者遵守。`check` 通过不等于它们已经做到。

- 从初步观察写起，按真实过程说明看到了什么、为什么这样判断、做了什么、得到什么。末节之后不追加附录。
- 原件 hash、环境、失败记录和验证日志留在题目目录。WP 不写验旗自证、提交状态或内部证据路径。解题必需的请求、响应、代码和中间值写在对应步骤。
- 脚本参与求解时，在完整 flag 前增加独立编号的「完整利用脚本」，粘贴实际使用的完整脚本、依赖和调用方式。调用说明不写本机绝对路径。前文仍要解释关键推导。
- 句子直接、具体，保留代码、参数、公式和真实输出，不编造经历。若环境提供 `humanizer` 技能，可以用来润色；润色不改变技术事实。
- 凭据不写入 WP。截图若用来支撑推理，正文还要有可复核的文字证据。

按题型至少写清：

- Reverse：关键函数的定位依据、数据流、位宽、端序、常量、逆变换或约束，以及如何验证候选。
- Web：正常请求、信任边界、漏洞原语、payload 和响应数据链。
- Crypto：参数来源、利用条件、公式、整数/字节转换、端序，以及代入或重加密结果。
- Pwn：架构、保护、偏移、原语、地址、链字段的目的、调用约定和实际交互结果。
- Misc/取证：文件结构、提取参数、每层产物和解码顺序。

模板以 `prep/templates/WP.template.md` 为准。`skills/whuctf-solver/assets/WP.template.md` 是同一文件的副本，方便技能目录单独拷贝；两份必须保持一致。
